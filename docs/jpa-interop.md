# Sharing one Postgres with a Spring Data JPA service

A go-boot service and a Spring Data JPA service can read and write the same database. This
page is the convention that makes it work.

Everything here was measured against Hibernate 6.6.11 and PostgreSQL 18.3, with a Go writer
on the same tables. The one exception is the lint's test fixture, which is Hibernate 7.4.1 and says
so where it is used. The evidence is in
[`docs/research/jpa-interop.md`](research/jpa-interop.md).

## The one rule that loses data

**Every Go `UPDATE` to a table with a `version` column must write `version = version + 1`.**

```sql
UPDATE customer SET first_name = $1, version = version + 1 WHERE id = $2;
```

A JPA `@Version` field is optimistic locking. Hibernate updates with
`... WHERE id = ? AND version = ?`. If your Go write leaves `version` alone, that predicate
still matches, so Hibernate commits over your write. **Nothing raises an error. On either
side.** Your write is gone.

With the bump, Hibernate's predicate misses, and it raises `StaleObjectStateException` — which
is the whole point of the column. Measured both ways.

## Pick one owner for the schema

Two tools cannot both own a schema. Each writes its own bookkeeping table and they will fight.

**Prefer the JPA side when a Spring service already exists.** This is not a preference about
which is nicer. Hibernate can generate *and* validate its own schema; go-boot cannot read Java
classes and so can never confirm a match. Letting the JPA side own the schema removes the
verification problem instead of solving it.

### When the JPA side owns it

Pass `nil` migrations to the database Starter:

```go
pool, dbc, err := db.New(cfg.DB, log, nil)
```

`nil` skips both the migration run and the pending-migration refusal (see
[ADR 0007](adr/0007-migrations-refuse-to-start.md)). You still get the pool and the readiness
Check. Do not run goose against a Hibernate-owned schema.

### When go-boot owns it

Write goose migrations that follow the table below, then prove it in CI:

1. Start a Postgres.
2. Run your migrations: `myservice migrate`.
3. Boot the Java service with `spring.jpa.hibernate.ddl-auto=validate`.

**Only Hibernate can confirm the schema matches its entities, so this step is not optional.**
It does put a JVM in your CI. That is fine for a repo that already has one. If you have no JVM,
you have no JPA service either, and this page does not apply to you.

## The convention

| The JPA side writes | The column it creates | What the Go side does |
|---|---|---|
| naming (Spring Boot default) | `Customer` → `customer`, `firstName` → `first_name` | nothing — this already matches Go and sqlc |
| `@Version` | `version bigint` | **`version = version + 1` on every update** |
| `@Id @GeneratedValue(IDENTITY)` | `generated by default as identity` | **prefer this** — plain `INSERT … RETURNING id` |
| `@Id @GeneratedValue` (default) | a sequence, `increment by 50` | `nextval` is safe, but each Go row burns 50 ids |
| `@Enumerated` (default) | `smallint` + a range check | **avoid** — the number is the Java enum's declaration order, so reordering the Java enum silently changes the meaning of stored rows |
| `@Enumerated(EnumType.STRING)` | `varchar(255)` + a value check | **use this** |
| `Instant` | `timestamp(6) with time zone` | maps cleanly |
| `LocalDateTime` | `timestamp(6)`, no zone | avoid — the UTC offset is lost |
| `UUID` | `uuid` | pgx handles it |
| `BigDecimal` | `numeric(38,2)` | needs a Go decimal type; `float64` is wrong |

**Sharing a Hibernate sequence is safe.** This surprises people, so it was measured: two
writers, 80 rows, zero duplicate keys. Hibernate takes its block of 50 ids from a real
`nextval`, and so does Go, and two `nextval` calls cannot return overlapping ranges. The cost is
waste, not correctness. Use `IDENTITY` anyway and the question does not arise.

## The lint

```go
func TestSchemaFollowsJPAConventions(t *testing.T) {
	db := dbtest.Start(t, migrations)
	dbtest.LintJPAConventions(t, db)
}
```

It reads `information_schema` and reports three things:

- an identifier that is not `lower_snake_case`
- a `timestamp without time zone` column
- a table with no `version` column

It skips the bookkeeping tables of goose, Flyway and Liquibase.

That skip is load-bearing, not tidy. `goose_db_version` has a `tstamp timestamp` column and no
`version` column, so without it the lint fails every schema go-boot creates — there is a test that
removes the skip and shows exactly that.

The lint's own tests run it against a schema **Hibernate generated** — Hibernate 7.4.1, from two
entities that follow this page — and it reports nothing. Hand-roll the same two tables without
reading the page and it reports all three findings.

A schema Hibernate wrote is not clean by itself. It is clean because the *entities* followed this
page. Default entities give you `LocalDateTime`, and the table above says to avoid it for the
reason the lint flags it: the offset is lost.

**It checks this convention. It does not check your JPA model, and it cannot.** go-boot never
sees your Java classes. Only `ddl-auto=validate` can confirm that a schema matches a particular
entity. Run both. Neither replaces the other:

| | `ddl-auto=validate` | `LintJPAConventions` |
|---|---|---|
| missing table, column or sequence | catches | misses |
| `timestamp` where JPA wants a time zone | **passes it silently** | catches |
| `varchar(10)` where JPA wants `varchar(255)` | **passes it silently** | misses — the length lives in the Java class |
| identifier that is not `lower_snake_case` | not tested — it compares against whatever names the entity declares | catches |

**Lint the schema you own.** On a schema you inherited from Hibernate, run it once to see what
you are dealing with, then stop. You cannot fix what you do not own, and it will report a false
positive on every `@ManyToMany` join table, because Hibernate never puts `@Version` on one.

## What go-boot does not give you

There is no `Repository` interface and no `Entity` type, and there will not be one. Sharing a
database is a property of the schema, not of any Go type — a Repository abstraction would not
have helped with a single rule on this page. See
[ADR 0009](adr/0009-no-repository-abstraction.md). Use `sqlc`, `ent`, `gorm` or hand-written
SQL. go-boot hands you a plain `*sql.DB` and stays out of it.
